# Agent Note: OpenCode 服务器启动时限

Status: implemented

[English](2026-09-08-opencode-startup-deadline.md) | 中文

## 问题

Windows 上 OpenCode 的冷启动可能超过 SDK 默认的五秒时限。一次激活工作流记录的执行器失败耗时为 5818 毫秒；隔离的 SDK 启动重现了五秒超时，而相同启动使用六十秒时限时在 12961 毫秒后就绪。通用提供方诊断无法向操作人员说明这一差异。

## 决策

真实适配器要求显式启动时限。Plurora 可执行程序默认提供六十秒，并在创建资源之前验证 `PLURORA_OPENCODE_STARTUP_TIMEOUT_MS`。该时限覆盖就绪等待，而非提示词执行。SDK 继续负责自己的计时器、取消和启动失败时的终止操作。

与 SDK 启动超时完全匹配的异常转换为 `OpencodeStartupTimeoutError`，其有界说明仅包含配置的时长。其他异常保留现有的通用诊断。启动超时仍是提供方失败，不触发自动回退。

## 考虑过的替代方案

**保留 SDK 默认值并重试。** 观察到的冷启动超过该时限；重试无法解决时限问题，还可能掩盖可复现的失败。

**增加外层启动器的健康检查时限。** 失败的计时器属于宿主已健康后启动的阶段级 OpenCode 服务器，因此启动器无法改变它。

**取消启动时限。** 永不宣布就绪的服务器仍需要有界失败和取消路径。

## 影响

缓慢但健康的启动可以完成，而失败的启动可能需要更长时间才会报告。操作人员无需修改固定版本的 checkout 即可调整时限。修改设置后需要新宿主进程。

SDK 边界测试覆盖延迟就绪、超时诊断、敏感信息隐藏和取消。组合后的 Plurora 快照记录 delivery 之前的启动失败。本地启动复现不发送模型请求；它不认证完整的真实 canary 测试，也不证明所有平台上的操作系统资源清理。
